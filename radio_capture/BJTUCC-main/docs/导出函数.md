# DC_CommonSocket.dll 设备控制导出函数说明

> 说明：以下内容针对 `DC_CommonSocket.dll` 中真正用于设备控制的 8 个 `DDDCXX*` 导出函数。该 DLL 还导出了大量 `cJSON` 辅助函数，但它们属于 JSON 处理库，不是设备采集控制接口。

## 基本结论

`DC_CommonSocket.dll` 是一个 32 位 PE DLL，主要作为 Qualcomm/common 类设备的控制器候选实现。它通过以下 8 个导出函数完成设备控制生命周期：创建实例、配置端口、连接采集、恢复、发送设备信息、发送命令、断开连接、释放实例。

`send` 目录中的 Qualcomm Trace 实际使用 `DDDCXX01.dll`。该 DLL 的导出编号与 `DC_CommonSocket.dll` 不同：`DDDCXX05` 是连接、`DDDCXX06` 是恢复、`DDDCXX07` 是命令、`DDDCXX08` 是内置 StartLog/芯片信息；其变长信息结构为 8 字节头后紧跟 payload，而不是第 8 字节存放 payload 指针。

设备控制函数通常按 Cdecl 调用；日志回调 `Log_CallBack` 单独按 StdCall 调用。实际返回码含义、结构体布局和调用顺序仍需要在目标 Windows 设备环境中实测确认。

## 设备控制函数列表

| 导出函数 | 功能定位 | 主要用途 | 典型参数/返回 |
|---|---|---|---|
| `DDDCXX01` | 创建设备控制实例 | 创建 native 设备控制对象，后续所有配置、连接和断开操作都依赖它返回的 handle。 | 输入 `module_id`；返回 opaque handle，空指针通常表示创建失败。 |
| `DDDCXX04` | 配置端口或连接信息 | 下发一项端口/连接配置，例如 Trace 端口、AT 端口、Modem 端口、网卡、ADB、UE IP、PC IP、波特率或 JSON 配置。 | 输入 `handle` 和 `TDCConnectInfo*`；返回 native 状态码。 |
| `DDDCXX05` | 建立连接并注册回调 | 使用已配置的端口连接设备，并注册 `Log_CallBack`，开始接收设备产生的实时日志数据。 | 输入 `handle`、callback、用户参数 `p_param`、超时时间；返回 native 状态码。 |
| `DDDCXX06` | 恢复操作 | 在设备异常、断线或需要恢复采集链路时调用。它是否重新打开端口、是否需要重新连接，要结合具体 profile 实测。 | 输入 `handle`；返回 native 状态码。 |
| `DDDCXX07` | 发送芯片/设备信息 | 向 native 控制器或设备下发芯片信息、设备信息等辅助连接数据。调用时机可能是连接前或连接后，需要按设备 profile 验证。 | 输入 `handle`；返回 native 状态码。 |
| `DDDCXX08` | 发送设备控制命令 | 发送 QMI、PPP 或其他设备命令，例如 Attach、Connect、Disconnect、Detach、SetAPN、拨号、挂断等。 | 输入 `handle` 和 `TDCCommandInfo*`；返回 native 状态码。 |
| `DDDCXX09` | 断开连接 | 停止设备连接和采集线程，结束 native 侧采集流程。一般应在释放实例前调用。 | 输入 `handle` 和超时时间；返回 native 状态码。 |
| `DDDCXX0A` | 释放设备控制实例 | 释放 `DDDCXX01` 创建的 native 设备控制对象，清理 native 资源。 | 输入 `handle`；返回 native 状态码。 |

## 推荐调用顺序

```text
1. DDDCXX01  创建设备控制实例
2. DDDCXX04  逐项配置端口/连接信息
3. DDDCXX07  可选：发送芯片/设备信息
4. DDDCXX05  建立连接并注册 Log_CallBack
5. DDDCXX08  可选：发送 QMI/PPP/设备命令
6. DDDCXX06  可选：异常后恢复
7. DDDCXX09  断开连接
8. DDDCXX0A  释放设备控制实例
```

## 回调相关说明

`DDDCXX05` 注册的日志回调签名可按以下形式理解：

```text
void __stdcall Log_CallBack(
    void*    pParam,
    int32    LogType,
    void*    LogBuffer,
    uint32   LogLen,
    uint64   CurTime
)
```

字段含义：

| 字段 | 含义 | 处理建议 |
|---|---|---|
| `pParam` | 用户传入的会话上下文指针 | 用于找回当前采集会话，不要依赖全局状态。 |
| `LogType` | native 给出的日志类型 | 先保存原始值，不能直接等同于 `msgCode`。 |
| `LogBuffer` | native 日志数据地址 | 必须在回调返回前复制为 Python 自有 bytes，不要保存裸指针。 |
| `LogLen` | 日志数据长度 | 按该长度复制，并做最大长度校验。 |
| `CurTime` | native 时间戳 | 时间单位和 epoch 未确认，先保存原始 `uint64`。 |

## 注意事项

- 当前导出表中没有 `DDDCXX02` 和 `DDDCXX03`，不要在代码中假设它们存在。
- `TDCConnectInfo` 和 `TDCCommandInfo` 都包含变长 `Value` 数据，Python 侧需要保证 header 和 payload 在 native 调用期间一直有效。
- 返回码不能简单假设为 `0` 成功或 `1` 成功，第一阶段应记录原始返回值并通过实测归纳。
- `DC_CommonSocket.dll` 是 32 位 DLL，只能被 32 位进程加载；64 位 Python 不能直接加载它。

# DDDIXX00.dll 与 DDDIXXS0.dll 导出函数说明

> 说明：以下内容针对 `DDDIXX00.dll` 和 `DDDIXXS0.dll` 的实际导出表。随包文档只作为参考；函数是否可正常工作、返回码语义、输出 buffer 格式和插件路由结果，都需要在目标 Windows 32 位环境中实测确认。

## 基本结论

这两个 DLL 都是 32 位 PE DLL，不能被 64 位 Python 直接加载。

- `DDDIXX00.dll`：日志解码入口/分派器。实际导出 `DDDIXX01` 到 `DDDIXX06` 共 6 个函数，并且导入了 `LoadLibraryExA`、`GetProcAddress`，说明它会在运行时按设备或模块条件加载其他 `DDDIXX*` 插件。
- `DDDIXXS0.dll`：一个具体解码插件候选。实际导出 `DDDIXX01` 到 `DDDIXX05`，没有导出 `DDDIXX06`；同时静态导出了大量 `cJSON` 辅助函数。

## DDDIXX00.dll 导出函数

| 导出函数 | 功能定位 | 主要用途 | 典型参数/返回 |
|---|---|---|---|
| `DDDIXX01` | 创建解码实例 | 根据设备/模块 ID 创建 native codec handle。上层一般先调用它，再执行配置或解码。 | 输入 `module_id`；返回 codec handle，空指针通常表示创建失败。 |
| `DDDIXX02` | 配置解码实例 | 向 codec 传入配置数据，例如解码配置、logmask 或其他 profile 相关 bytes。具体 `config_id` 含义需要实测。 | 输入 `handle`、配置编号、配置 buffer、长度；返回 native 状态码。 |
| `DDDIXX03` | raw message 转 detail | 将一条原始日志消息按 `msg_code` 解码为 detail bytes，可能是 XML、文本、表格化内容或插件自定义格式。 | 输入 `handle`、`msg_code`、源 buffer、输出长度指针、输出 buffer；返回 native 状态码。 |
| `DDDIXX04` | 获取显示格式 | 根据 `msg_code` 获取 table/display format，辅助上层判断 detail 输出应该按什么格式解析。 | 输入 `handle`、`msg_code`、输出 format 指针；返回 native 状态码。 |
| `DDDIXX05` | 释放解码实例 | 释放 `DDDIXX01` 创建的 codec handle，清理 native 资源。 | 输入 `handle`；返回 native 状态码。 |
| `DDDIXX06` | 获取标准 Bin buffer | 尝试把 raw message 解码为标准 Bin 或标准结构化 bytes。是否可用取决于实际路由到的插件能力。 | 输入 `handle`、`msg_code`、源 buffer、输出长度指针、输出 buffer；返回 native 状态码。 |

## DDDIXXS0.dll 导出函数

`DDDIXXS0.dll` 的解码接口只有 5 个：

| 导出函数 | 功能定位 | 主要用途 | 与 `DDDIXX00.dll` 的区别 |
|---|---|---|---|
| `DDDIXX01` | 创建插件解码实例 | 创建 `DDDIXXS0` 插件自己的 codec handle。 | 与 `DDDIXX00.dll` 同名，但这里是具体插件实现。 |
| `DDDIXX02` | 配置插件解码实例 | 向插件传入配置 buffer。 | 具体配置项由插件决定，需要实测。 |
| `DDDIXX03` | raw message 转 detail | 将消息解码为 detail 输出。字符串中可见 LTE、NR、msgtype、Msglength 等字段痕迹，说明它包含无线日志 detail 解析逻辑。 | 这是插件实际执行 detail 解析的候选入口。 |
| `DDDIXX04` | 获取显示格式 | 获取某个 `msg_code` 对应的显示/表格格式。 | 供上层或分派器决定如何解释 detail 输出。 |
| `DDDIXX05` | 释放插件解码实例 | 释放插件 codec handle。 | 与创建函数配套使用。 |

注意：`DDDIXXS0.dll` **没有导出 `DDDIXX06`**。因此如果 `DDDIXX00.dll` 最终路由到 `DDDIXXS0.dll`，标准 Bin 功能可能不可用，应该优先保留 raw 数据并使用 `DDDIXX03` 的 detail 输出作为降级路径。

## 两个 DLL 的关系

推荐把 `DDDIXX00.dll` 当作上层稳定入口，把 `DDDIXXS0.dll` 当作被分派器加载的具体插件候选：

```text
Python / 上层程序
        |
        v
DDDIXX00.dll
  - DDDIXX01 创建解码实例
  - DDDIXX02 配置
  - DDDIXX03 detail 解码
  - DDDIXX04 display format
  - DDDIXX05 释放
  - DDDIXX06 标准 Bin
        |
        | 运行时 LoadLibraryExA / GetProcAddress
        v
DDDIXXS0.dll 或其他 DDDIXX* 插件
  - DDDIXX01 到 DDDIXX05
  - 具体执行某类设备/日志的 detail 解析
```

`DDDIXX00.dll` 字符串中可见多个插件名，例如 `DDDIXX03`、`DDDIXX05`、`DDDIXX08`、`DDDIXX0B`、`DDDIXX0D`、`DDDIXX0F`、`DDDIXX18`、`DDDIXXS0` 等。这说明它不是单纯的解码实现文件，而是带有插件选择/分派逻辑。

## cJSON 辅助函数

`DDDIXXS0.dll` 还导出了大量 `_cJSON_*` 函数，例如：

- `_cJSON_Parse@4`
- `_cJSON_Print@4`
- `_cJSON_PrintUnformatted@4`
- `_cJSON_CreateObject@0`
- `_cJSON_CreateArray@0`
- `_cJSON_AddItemToObject@12`
- `_cJSON_GetObjectItem@8`
- `_cJSON_Delete@4`

这些属于 JSON 处理库函数，不是日志解码业务接口。除非需要直接操作该 DLL 内部暴露的 cJSON 能力，一般不建议上层业务代码调用它们。

## 注意事项

- `DDDIXX00.dll` 导出 `DDDIXX01` 到 `DDDIXX06`；`DDDIXXS0.dll` 只导出 `DDDIXX01` 到 `DDDIXX05`。
- `DDDIXX06` 的标准 Bin 能力不能假设所有插件都支持。
- `msg_code` 不能直接用 `Log_CallBack` 的 `LogType` 代替，应该先从原始帧中确认消息头和消息编号。
- 输出 buffer 不应写死长度，建议从 64 KiB 起步，遇到容量不足或输出长度等于容量时扩容重试。
- 返回码含义需要记录原始值后通过样本和真实设备测试归纳，不能简单假设 `0` 或 `1` 一定代表成功。
