# Windows Python DLL 无线数据采集技术开发文档指南

版本：v1.0  
整理日期：2026-08-18  
适用范围：Windows x86、Python、Qualcomm/common 类设备实时无线日志采集 MVP。

## 1. 文档目标

本文用于指导后续开发人员完成一套基于 Python 的 Windows 无线数据采集程序，覆盖从配置加载、DLL 适配、设备连接、native callback、原始数据落盘、帧解析、日志解码、结构化输出到回放诊断的完整链路。

本阶段的核心目标不是一次性兼容所有原生格式，而是先保证：

- 原始 callback 数据可靠保存；
- native ABI 和 DLL 加载方式可验证；
- 设备会话生命周期可控；
- 解码失败不影响原始数据留存；
- 输出格式可以被回放、排错和后续扩展。

## 3. 总体架构

### 3.1 架构原则

1. **先原始落盘，再做解析解码**：callback 收到的数据必须先复制、入队、保存，不能因为解析失败丢掉原始帧。
2. **业务层不直接碰 ctypes 细节**：`ctypes`、调用约定、结构体布局、buffer 生命周期集中放在 `native/`。
3. **profile 驱动设备差异**：设备/EQ ID、控制器 DLL、端口编码、解码 module、插件预期、芯片信息下发时机都由 profile 管理。
4. **callback 尽快返回**：callback 线程只做内存复制和投递队列，不做磁盘 I/O、SQLite、解码、网络请求和复杂锁操作。
5. **返回码先记录原值**：native 返回码语义尚未完全确定，第一阶段不能统一假设 `0` 或 `1` 一定代表成功。
6. **所有未验证 ABI 都集中封装**：例如 `TDCConnectInfo.Value` 的变长布局，不能散落在业务代码里硬编码。

### 3.2 核心数据流

```mermaid
flowchart LR
    A[CLI/YAML/JSON 配置] --> B[DeviceSessionConfig]
    B --> C[ProfileResolver]
    C --> D[x86 与 DLL 校验]
    D --> E[Win32NativeLoader]
    E --> F[DC_CommonSocket 控制器]
    F --> G[TDCConnectInfo 逐项端口配置]
    G --> H[DDDCXX05 连接并注册 Log_CallBack]
    H --> I[native 设备采集]
    I --> J[callback 立即复制 LogBuffer]
    J --> K[FrameEnvelope]
    K --> L[有界队列]
    L --> M[RawWriter 原始二进制与 JSONL 索引]
    L --> N[FrameParser 提取 msg_code/payload]
    N --> O[DecodeRequest]
    O --> P[DDDIXX00 解码分派器]
    P --> Q[DDDIXXS0 或匹配插件]
    Q --> R[DecodedRecord]
    R --> S[JSONL/SQLite/normalized_json]
    M --> T[ReplayReader 离线回放与故障诊断]
```

关键边界：

- `Log_CallBack` 参数明确提供的是 `LogType`、`LogBuffer`、`LogLen`、`CurTime`，不直接提供已确认的 `msgCode`。
- `DDDIXX03`、`DDDIXX06` 需要 `msg_code`，因此必须设计 `FrameParser`，不能把 `LogType` 未经验证地当作 `msgCode`。
- `CurTime` 单位和 epoch 待实测，raw 层必须同时保存 native 原始时间和 Python 接收时间。

## 4. 运行时和 DLL 边界

### 4.1 必需运行环境

- 操作系统：Windows。
- Python：32 位 CPython。
- DLL 架构：当前核心 DLL 均为 PE32/Intel 80386，64 位 Python 不能直接加载。
- 运行时：需要 `msvcp120.dll`、`msvcr120.dll` 与核心 DLL 同目录或在受控搜索路径中。

启动时必须检查：

```python
import ctypes
import platform
import struct

assert platform.system() == "Windows"
assert struct.calcsize("P") * 8 == 32
assert ctypes.sizeof(ctypes.c_void_p) == 4
```

### 4.2 核心 DLL

| DLL | 职责 | 当前策略 |
|---|---|---|
| `DC_CommonSocket.dll` | Qualcomm/common 设备控制器候选，负责端口配置、连接、callback、恢复、命令发送和断开。 | MVP 默认控制器，但不能写死为所有设备通用控制器。 |
| `DDDIXX00.dll` | 日志解码分派器，导出 `DDDIXX01` 到 `DDDIXX06`，运行时按 EQ ID 加载插件。 | Python 上层只直接调用分派器，不绕过它固定调用某个插件。 |
| `DDDIXXS0.dll` | 当前 Qualcomm EQ ID 的默认解码插件候选。 | 先作为默认候选；`DDDIXX06` 标准 Bin 能力需要实测。 |
| `msvcp120.dll` | VC++ 2013 C++ 运行时。 | 与核心 DLL 同目录管理。 |
| `msvcr120.dll` | VC++ 2013 C 运行时。 | 与核心 DLL 同目录管理。 |

`DDDIXX00.dll` 会使用 `LoadLibraryExA` 按文件名加载插件，因此核心 DLL 和插件必须保持在同一个受控目录中，不要随意重命名或拆分。

### 4.3 暂不进入 MVP 默认链路的 DLL

| DLL | 原因 |
|---|---|
| `DDFPXX00.dll` | 面向 QMDL、DTLog、UBO 等离线文件解析/转换，且依赖 `libcrypto.dll`、`libssl.dll` 等，不属于 live callback MVP。 |
| `AADDCC.dll` | 面向原生 UBO/SQLite 数据访问；当前先用 Python 自有 raw/JSONL/SQLite，UBO 写出放到第二阶段。 |
| `SGQmicm.dll` | 独立 QMI SDK；当前 QMI 命令优先通过设备控制器 `DDDCXX08` profile 暴露。 |
| 其他 `DC_*.dll`、`DDDIXX*.dll` | 由其他设备厂商、EQ ID 或芯片 profile 使用，需要单独验证映射和 ABI。 |

### 5.2 配置字段到 native 的映射

| Python 字段 | native 目标 | 说明 |
|---|---|---|
| `eq_id` | `module_id` / codec module | 创建设备控制器和 codec 时使用，具体语义由 profile 确认。 |
| `trace_port` | `TDCConnectInfo(Type=1)` | 主 Trace 端口，整数 payload 首版建议 little-endian `uint32`，需实测。 |
| `at_port` | `TDCConnectInfo(Type=2)` | AT 串口。 |
| `net_adapter` | `TDCConnectInfo(Type=3)` | 网卡字符串，编码和是否带 NUL 由 profile 决定。 |
| `modem_port` | `TDCConnectInfo(Type=4)` | Modem 串口。 |
| `adb_port` | `TDCConnectInfo(Type=5)` | ADB 端口，整数或字符串由 profile 决定。 |
| `trace_nr_port` | `TDCConnectInfo(Type=6)` | 辅助/NR Trace 候选映射，需要设备实测确认。 |
| `ue_ip` | `TDCConnectInfo(Type=7)` | UE IP 字符串。 |
| `pc_ip` | `TDCConnectInfo(Type=8)` | PC IP 字符串。 |
| `baud_rate` | `TDCConnectInfo(Type=9)` | 波特率。 |
| `json_config` | `TDCConnectInfo(Type=999)` | JSON 设备配置，先保存 UTF-8 bytes。 |

端口配置必须逐项调用 `DDDCXX04(handle, info_ptr)` 并记录返回码，不能把多个端口拼成一个未验证的复合结构。

## 6. 会话运行流程

### 6.1 标准流程

1. `cli.py` 读取启动参数和配置文件。
2. `config.py` 生成并校验 `DeviceSessionConfig`。
3. `profiles.py` 根据 `eq_id`、`chip_type`、`eq_type` 选择控制器 DLL、codec module、端口编码和芯片信息下发策略。
4. `win32_loader.py` 校验 x86、DLL 路径、SHA-256、PE 架构、导出函数和依赖。
5. `controller.py` 调用 `DDDCXX01(module_id)` 创建设备控制实例。
6. `callbacks.py` 创建 `SessionContext` 和 `LOG_CALLBACK`，并由 `CaptureSession` 持有强引用。
7. `controller_abi.py` 把端口字段转换为 `OwnedDCInfo`，逐项调用 `DDDCXX04`。
8. 按 profile 决定是否调用 `DDDCXX07` 发送芯片信息，必要时用 `DDDCXX08` 下发命令。
9. 调用 `DDDCXX05(handle, callback, p_param, timeout_ms)` 建立连接。
10. callback 收到 native buffer 后立即复制为 Python-owned bytes，生成 `FrameEnvelope` 并放入有界队列。
11. `RawWriter` 先保存原始 envelope。
12. `FrameParser` 尝试识别消息头、`msg_code` 和 payload。
13. `LogCodec` 通过 `DDDIXX00.dll` 创建 codec，并调用 detail/standard-bin/display-format 接口。
14. `ResultStore` 将 `DecodedRecord` 写入 JSONL 或 SQLite。
15. 停止时先设置停止标记，再断开设备、等待 worker、释放 native handle、释放 callback 强引用、最后卸载 DLL。

### 6.2 状态机

```text
NEW
  -> CONFIG_LOADED
  -> DLL_LOADED
  -> INSTANCE_CREATED
  -> PORTS_CONFIGURED
  -> CONNECTED
  -> CAPTURING
  -> STOPPING
  -> CLOSED
```

任意阶段都可以进入 `ERROR`。资源释放顺序必须反向执行：

1. 设置 `stopping=True`，callback 不再派发新业务任务。
2. 调用 `DDDCXX09(handle, timeout_ms)` 断开设备。
3. 等待 raw writer、decoder worker、storage worker 结束或超时。
4. 必要时调用 `DDDCXX06(handle)` 做恢复。
5. 调用 `DDDCXX0A(handle)` 释放控制器实例。
6. 释放 callback、`pParam`、端口 payload、输出 buffer 等 Python 强引用。
7. 确认没有 callback 仍在执行后，才卸载 DLL。

## 8. Native ABI 设计

### 8.1 调用约定

- 设备控制函数：Cdecl。
- 日志 codec 函数：Cdecl。
- `Log_CallBack`：StdCall。

Python 不能把所有函数统一写成 `WINFUNCTYPE` 或统一写成 `CFUNCTYPE`。建议：

```python
import ctypes as C

CDECL = C.CFUNCTYPE

LOG_CALLBACK = C.WINFUNCTYPE(
    None,
    C.c_void_p,   # pParam
    C.c_int32,    # LogType
    C.c_void_p,   # LogBuffer
    C.c_uint32,   # LogLen
    C.c_uint64,   # CurTime
)
```

### 8.2 控制器导出

| 导出 | ctypes 等价签名 | 职责 |
|---|---|---|
| `DDDCXX01` | `c_void_p(c_int32)` | 创建设备控制实例。 |
| `DDDCXX04` | `c_int32(c_void_p, c_void_p)` | 配置一项端口或设备信息。 |
| `DDDCXX05` | `c_int32(c_void_p, LOG_CALLBACK, c_void_p, c_uint32)` | 建立连接并注册 callback。 |
| `DDDCXX06` | `c_int32(c_void_p)` | 恢复。 |
| `DDDCXX07` | `c_int32(c_void_p)` | 发送芯片信息。 |
| `DDDCXX08` | `c_int32(c_void_p, c_void_p)` | 发送 QMI/PPP 或设备命令。 |
| `DDDCXX09` | `c_int32(c_void_p, c_uint32)` | 断开。 |
| `DDDCXX0A` | `c_int32(c_void_p)` | 释放控制器实例。 |

不要推导 `DDDCXX02` 或 `DDDCXX03` 一定存在，当前核心控制器导出表中没有它们。

### 8.3 `TDCConnectInfo` 和 `TDCCommandInfo`

逻辑字段：

```text
TDCConnectInfo
  Type: uint32
  Len: uint32
  Value: bytes

TDCCommandInfo
  Type: uint32
  Len: uint32
  Value: bytes
```

关键约束：

- `Len` 必须等于 `Value` 的实际字节长度。
- `Value` 是变长数据，真实 native 布局可能是 inline bytes，也可能是指针布局，必须实测。
- Python 封装对象必须同时持有 header 和 payload，保证 native 调用返回前地址有效。
- 字符串 payload 是否需要 NUL 结尾，由 profile 决定。
- 命令 payload 只由 profile 编码，底层接口不解释业务字段。

命令类型：

```text
QMI_Attach=1
QMI_Connect=2
QMI_Disconnect=3
QMI_Detach=4
QMI_SetAPN=5
PPP_DialUp=257
PPP_HangUp=258
```

### 8.4 解码器导出

| 导出 | ctypes 等价签名 | 职责 |
|---|---|---|
| `DDDIXX01` | `c_void_p(c_int32 module_id)` | 创建 codec 实例。 |
| `DDDIXX02` | `c_int32(c_void_p, c_int32, c_void_p, c_int32)` | 配置 codec。 |
| `DDDIXX03` | `c_int32(c_void_p, c_uint32, c_int32, POINTER(c_ubyte), POINTER(c_int32), POINTER(c_ubyte))` | raw message 转 detail buffer。 |
| `DDDIXX04` | `c_int32(c_void_p, c_uint32, POINTER(c_int32))` | 获取 display format。 |
| `DDDIXX05` | `c_int32(c_void_p)` | 释放 codec 实例。 |
| `DDDIXX06` | `c_int32(c_void_p, c_uint32, c_int32, POINTER(c_ubyte), POINTER(c_int32), POINTER(c_ubyte))` | 获取标准 Bin buffer。 |

输出 buffer 建议从 64 KiB 起步。若返回容量不足、输出长度等于容量、或返回码显示可重试，则扩容后重试。具体返回码语义通过 fixture 统计维护到 profile 中。

## 10. 存储和输出设计

### 10.1 原始文件

建议 raw 输出采用 session 目录和滚动文件：

```text
data/raw/<session_id>/frames-000001.bin
data/raw/<session_id>/frames-000001.jsonl
```

每帧最少保存：

```text
sequence: uint64
receive_time_ns: uint64
native_cur_time: uint64
log_type: int32
payload_length: uint32
payload: bytes
```

`frames-*.jsonl` 是索引和诊断信息，不替代二进制 payload。后续若生成 UBO/DTLog，应新增专门 writer，不要在 raw writer 中改变字段含义。

### 10.2 SQLite 最小表

```sql
CREATE TABLE capture_session (
    session_id TEXT PRIMARY KEY,
    eq_id INTEGER NOT NULL,
    chip_type TEXT NOT NULL,
    controller_dll TEXT NOT NULL,
    codec_module_id INTEGER,
    started_at TEXT NOT NULL,
    stopped_at TEXT,
    status TEXT NOT NULL
);

CREATE TABLE raw_frame (
    session_id TEXT NOT NULL,
    sequence INTEGER NOT NULL,
    native_cur_time INTEGER NOT NULL,
    receive_time_ns INTEGER NOT NULL,
    log_type INTEGER NOT NULL,
    payload BLOB NOT NULL,
    PRIMARY KEY (session_id, sequence)
);

CREATE TABLE decoded_record (
    session_id TEXT NOT NULL,
    sequence INTEGER NOT NULL,
    module_id INTEGER,
    msg_code INTEGER,
    display_format INTEGER,
    return_code INTEGER NOT NULL,
    standard_bin BLOB,
    detail BLOB,
    normalized_json TEXT,
    error TEXT,
    PRIMARY KEY (session_id, sequence)
);
```

### 10.3 输出分阶段策略

| 阶段 | 输出内容 | 目标 |
|---|---|---|
| MVP | raw 二进制、JSONL 索引、Python SQLite | 保证可追踪、可回放、可诊断。 |
| 兼容读取 | 通过 `DDFPXX00.dll` 读取/转换已有 UBO/QMDL/DTLog | 建立 fixture 和字段对照。 |
| 兼容写出 | 通过 `AADDCC.dll` 生成原生 UBO | 与参考工具打开/查询结果对照后再启用。 |

## 11. 对外 Python API 建议

业务层应依赖稳定类接口，不直接接触 `ctypes` 函数指针。

```python
class CaptureSession:
    def open(self, config: DeviceSessionConfig) -> None: ...
    def configure_ports(self) -> None: ...
    def connect(self) -> None: ...
    def start_workers(self) -> None: ...
    def stop(self, timeout: float = 10.0) -> None: ...
    def recover(self) -> None: ...
    def close(self) -> None: ...


class DeviceController:
    def create(self, module_id: int) -> None: ...
    def configure_port(self, type_id: int, payload: bytes) -> int: ...
    def send_chip_info(self) -> int: ...
    def send_command(self, type_id: int, payload: bytes) -> int: ...
    def connect(self, callback, user_param, timeout_ms: int) -> int: ...
    def recover(self) -> int: ...
    def disconnect(self, timeout_ms: int) -> int: ...
    def close(self) -> int: ...


class LogCodec:
    def create(self, module_id: int) -> None: ...
    def configure(self, config_id: int, payload: bytes) -> int: ...
    def get_detail(self, msg_code: int, payload: bytes) -> bytes: ...
    def get_display_format(self, msg_code: int) -> tuple[int, int]: ...
    def get_standard_bin(self, msg_code: int, payload: bytes) -> bytes: ...
    def close(self) -> int: ...
```

`start_workers()` 是 Python 侧线程启动动作，不对应某个 native “启动采集”函数。真正启动设备采集的是 `DeviceController.connect()` 内部的 `DDDCXX05`。

## 12. 开发实施顺序

### 阶段一：环境与 ABI 基线

目标：无设备情况下确认 Python 位数、DLL 文件、导出函数和基本绑定可用。

交付物：

- x86 Python 检查。
- DLL 文件名、大小、SHA-256、PE 架构检查。
- `DC_CommonSocket.dll` 8 个导出绑定报告。
- `DDDIXX00.dll` 6 个导出绑定报告。
- `TDCConnectInfo`、`TDCCommandInfo` 布局探测代码。
- `NativeCallError` 基础封装。

### 阶段二：设备会话和原始采集

目标：用单端口、默认 logmask 完成 callback 数据接收和原始落盘。

交付物：

- `DeviceSessionConfig -> TDCConnectInfo` 字段映射。
- `DDDCXX01`、`DDDCXX04`、`DDDCXX05`、`DDDCXX09`、`DDDCXX0A` 会话封装。
- `SessionContext`、callback、handle、payload owner 生命周期管理。
- 有界队列、队列满计数、停止策略。
- raw 二进制文件和 JSONL 索引。
- 单端口短时采集样例。

### 阶段三：帧解析与日志解码

目标：从 raw fixture 中确认 `msg_code` 规则，并通过 `DDDIXX00.dll` 得到 detail 或标准 Bin。

交付物：

- `FrameParser` 对消息头、`msg_code`、payload 的识别。
- `DDDIXX01` 到 `DDDIXX06` 的 `LogCodec` 封装。
- 输出 buffer 扩容重试机制。
- `DecodeRequest -> DecodedRecord` 数据流。
- 解码失败降级策略。
- 固定 fixture 的重复解码结果。

### 阶段四：结构化输出、回放和稳定性

目标：形成可回放、可追踪、可验收的工程版本。

交付物：

- `ReplayReader` 离线重放。
- SQLite 表和写入事务。
- fixture 驱动的字段归一化。
- 30 分钟稳定性测试。
- 断连、恢复、重连、队列积压和异常退出测试。
- 部署说明、接口测试记录、性能指标和问题清单。

## 14. 已知风险与处理方式

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 设备到控制器 DLL 的映射未完全确定 | 可能选错 `DC_*.dll`。 | 放到 profile 中，首版只支持 Qualcomm/common MVP，并记录实际选择。 |
| `TDCConnectInfo.Value` native 布局未确认 | 可能配置失败或进程崩溃。 | 集中封装 `OwnedDCInfo`，先做尺寸、偏移和地址探测。 |
| `LogType` 不等于 `msgCode` | 解码输入错误。 | raw 先落盘，开发 `FrameParser`，用 fixture 验证。 |
| `CurTime` 单位未知 | 时间轴错位。 | 同时保存 native 原始时间和 Python 接收时间。 |
| `DDDIXXS0.dll` 未确认支持 `DDDIXX06` | 标准 Bin 可能不可用。 | 首版以 detail/raw 降级为可靠路径。 |
| `DDDIXX00.dll` 插件搜索路径错误 | 文件存在但 native 加载失败。 | 核心 DLL 同目录、绝对路径加载、记录搜索路径。 |
| logmask 下发接口未完全恢复 | 只能使用默认 logmask。 | 首版支持 default，后续通过 `DDDCXX08` 或 JSON config 实测扩展。 |
| native 返回码语义未知 | 成功/失败判断错误。 | 保存原始返回码，通过 profile 维护成功码集合。 |
| 授权和许可边界 | 运行失败或合规风险。 | 不实现 license 绕过，只在已授权环境加载和测试。 |

## 15. 开发注意事项

- 不要把 DLL 复制到 `System32`，使用项目内受控 `dll/` 目录。
- 不要依赖用户当前工作目录加载插件，使用绝对路径和受控 DLL 搜索路径。
- 不要在 callback 中写 SQLite、写文件、调用 decoder 或做网络请求。
- 不要保存 native `LogBuffer` 裸指针到队列。
- 不要把 `DDDIXX01.dll` 写死为 Qualcomm 必需插件；当前默认候选是 `DDDIXXS0.dll`，实际路由由 `DDDIXX00.dll` 决定并需实测。
- 不要在没有 fixture 的情况下猜测 RSRP、SINR、RRC 等字段偏移。
- 不要宣称 Python SQLite 等同于原生 UBO；UBO 写出必须等 `AADDCC.dll` ABI 和表结构确认后再做。
- 每次替换 DLL，必须同步更新大小、SHA-256、导出表、依赖和 smoke test 结果。

## 16. 最小可交付版本定义

MVP 完成的判定标准：

1. 32 位 Python 能启动并完成 DLL 静态校验。
2. `DC_CommonSocket.dll` 控制器导出绑定成功。
3. 能创建控制器实例，并逐项下发至少一个 Trace 端口配置。
4. 能通过 `DDDCXX05` 注册 callback 并接收数据。
5. callback 数据能复制为 `FrameEnvelope` 并进入有界队列。
6. 原始数据能写入 raw 二进制和 JSONL 索引。
7. 程序能按状态机停止、断开、释放，不崩溃、不悬挂。
8. 能用 raw fixture 离线回放，尝试解码并保存 `DecodedRecord`。
9. 解码失败时原始帧仍完整保留。
10. 形成测试记录和未验证 ABI 清单。
